Ostinato

An offline research prototype that studies whether a camera can estimate breathing and whether another viewpoint can recover an assessment when the first view fails.

Project scope

Ostinato’s long-term goal is a robot that helps responders locate and assess people after a disaster, including when communications are down. Today the desktop prototype monitors one person at a time. In simulation, a robot chooses viewpoints and visits multiple people, and an offline medic view displays the path, measured rates and reasons for human checks.

Research use only. Use people and data only as described in the trial protocol. When the system cannot obtain usable evidence, it reports “unable to assess.” An absent motion signal or an unseen response leaves breathing status unknown. The prototype has yet to publish validation against independently counted breaths.

How it works

  1. Locate and track the chest. MediaPipe Pose finds landmarks for one person. OpenCV tracks texture inside a chest region and in the background. Subtracting background motion helps account for small camera shifts. The tracker declines when there is insufficient detail or a usable background is missing.
  2. Estimate and check the rate. The monitor uses a rolling 30-second window. NumPy and SciPy resample and filter the signal, then check the frequency and periodicity of chest movement. The estimator needs about 25 seconds of usable history, works in a nominal 6–42 breaths/min range, and rejects weak, interrupted or unstable signals. Its quality score describes the signal.
  3. Choose the next action. The assessor waits for a stable rate, asks for another camera position when the view looks unsuitable, or asks a person to check when time or viewpoints run out. The live interface keeps a completed assessment and its timestamp visible alongside the current camera evidence.
  4. Look for a response. A local voice asks the person to raise one hand. The camera must see the hand down and then held up following the request. If speech fails, the interface can show the prompt. In the desktop app the operator moves the camera. Navigation runs in simulation.

What the project tests

Ostinato’s contribution is the combination of an explicit decision to withhold a rate, a second viewpoint and a trace that can replay the assessor with both view orders. The testable question is whether a new view improves the chance of an accurate reading within a practical time budget.

Skills developed

The chest tracker applies pose estimation and optical flow. The breathing estimator uses spectral analysis and rejection criteria. The assessor and voice prompt exercise state-machine design and human–robot interaction. The paired trial CLI turns those components into a reproducible experiment with accuracy and coverage measures.

Run locally

From a checkout, install with Python 3.10–3.12. Grant the operating system’s camera permission for live measurements. For the first run, sit still 1–2 m from a fixed camera with shoulders, chest and some background visible. Patterned clothing can help the tracker find usable points.

python3.10 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
ostinato
ostinato-sim scene 1001 --html medic.html

During an active live assessment, press V to request a hand raise. When asked to move, reposition the camera and press M. Use R to restart and Q to quit. Run ostinato --no-prompt to ask only on V, or ostinato --video path/to/clip.mp4 to analyze a local video with prompts disabled. Open the generated medic.html in a browser to see a simulated search.

Runtime uses the local camera or video and optional local speech. The app requires no account, API key, cloud service or network connection once dependencies are installed. If obtaining the checkout requires GitHub access, authenticate in GitHub or a local credential helper and keep the credentials local. The app processes frames in memory without writing images or video. Paired trial JSON contains counts, timing, rates, signal values and reasons. Keep these files in the ignored data/ folder and out of public artifacts.

Evidence and limits

A synthetic integration test exercises a blocked first view and a visible second view. It checks that the report counts one accurate recovery and that replay reaches a reading earlier when the visible view comes first. The test uses generated frames, fixed pose landmarks and scripted breath counts.

Across 100 synthetic scenes (seeds 0–99), the multi-person simulation reports that it measured 80.9% of people when it predicted viewpoints and 66.5% when it always picked the closest view. Its estimated urgency cue improves time to reach urgent simulated cases only when the cue carries useful information. The simulator assumes known locations and walls, and its rules for successful observations favor chest-direction prediction. The medic display’s attention order is illustrative.

Live readings can fail with occlusion, insufficient texture, camera motion, low-amplitude movement or unstable tracking. Additional people can make a raised hand hard to attribute. Noise, disability, injury and language can all affect whether someone can respond to a prompt. The device still needs paired volunteer results to estimate accuracy, coverage and the limits of generalizing to new views.

Evaluation plan

  1. Establish a reproducible baseline. Run the synthetic blocked-view test and existing suite. Record the commit, Python version and camera configuration for the pilot.
  2. Collect paired windows. With consenting healthy volunteers and an independent observer, mark a clear front view and a farther angled view. Alternate the order across pairs, keep lighting and camera settings fixed within pairs, and include a condition with partial occlusion. Each view starts with a fresh tracker. The observer counts during each 30-second window and records the count before seeing the estimate. Consult the institution about review requirements before research or publication.
  3. Report accuracy with coverage. Divide reported windows by all windows. Compute absolute error against each window’s manual reference and report mean absolute error over returned rates. Give the number of first-view declines, second-view returns and recoveries within the prespecified 2 breaths/min exploratory tolerance. One extra counted breath over 30 seconds changes the reference by 2 breaths/min. With sufficient pairs, report bias and limits of agreement, accounting for repeated windows per participant.
  4. Test the decision separately. Replay both orders using identical recorded evidence. Compare time to a usable reading and the fraction remaining unassessed. Capture actual repositioning time separately because replay budgets 30 seconds per view and models zero travel. Compare simulated policies on matched scenes and report time to reading alongside the unassessed fraction.
  5. Use the pilot to choose the next build. If accurate recoveries repeat across views and participants, test the viewpoint rule on held-out people and scenes. If recoveries are rare or inaccurate, inspect decline reasons and prioritize tracking before adding a mobile platform. Ask a responder which evidence would have changed an action in a past incident.

Research context

Camera-based breathing measurement
Massaroni et al. (2019) estimated respiratory rate from laptop RGB video in a controlled volunteer study using a wearable pressure signal for comparison. It establishes prior work on camera-based measurement. Sensors, 19(12), 2758
Robots in urban search and rescue
Casper and Murphy (2003) analyzed robot-assisted response at the World Trade Center and documented what information people and robots needed to exchange. Their findings frame the question of what an assessment should convey to a responder. IEEE Transactions on Systems, Man, and Cybernetics, Part B, 33(3), 367–385
Evaluating agreement
Bland and Altman (1986) describe how to analyze paired differences between measurement methods. This supports examining bias and limits of agreement alongside average error. The Lancet, 8476, 307–310
